# Research: M11 identity and access (invitations, MFA, SSO, platform API keys)

Date: 2026-11-06 (for the plan `plans/261107-1200-cyberlab-m11-identity/`). Scope: what CyberLab has today, the standards that bind the design, the libraries and images to use, and the choices with their reasons. Web facts were fetched on 2026-11-06 and must be re-checked by the phase that pins a version.

## 1. What exists (scout of the code, branch after M7)

- **Auth** (`app/modules/auth`): argon2id passwords (`core/security.py`, a dummy hash on unknown emails), a 15-min HS256 access JWT with `sub`, `fid` (refresh family), `jti`, `typ`; opaque 256-bit refresh tokens stored as sha256 in `refresh_tokens`, rotated atomically under a per-family advisory lock, reuse detection that revokes the family and denylists its access tokens in Redis (`denylist:fam:`), 7-day sliding / 30-day absolute session. Cookies `cl_access` (`/api`), `cl_refresh` (`/api/v1/auth`), `cl_csrf` (double submit), all `SameSite=Strict`. `auth_events` is an append-only, non-tenant log with no read API.
- **Users** are global (no RLS): `email` citext unique, `password_hash`, `display_name`, `is_active`. There is no email verification, no MFA, no "kind" (the M7 retention system user is an inactive row with the unusable hash `!unusable:retention-system-user`).
- **Membership**: `POST /orgs/{org}/members {email, role}` adds an **already registered** user directly, with no consent, and answers `404 user_not_found` for unknown emails (enumeration, rate limited 30 / 10 min). Roles owner / admin / analyst / viewer; only owners touch the owner role; org-row lock plus a role re-read for every membership change.
- **Rate limits**: Redis fixed windows (`core/rate_limit.hit`), login per IP (20 / min) and per email+IP failures (5 / 15 min), register per IP, org create, member add; M7 added a global per-user limit (600 / min) inside `current_user`.
- **Sealing**: `core/sealbox.py` is an X25519 + HKDF + AES-256-GCM sealed box per `SealDomain` (scheme in HKDF info and AAD; AAD `scheme|org|provider|kid|key_version|base_url_norm`; 8–256 printable ASCII plaintext). The API only seals; `sealbox_open.py` may be imported only by `threat_intel/unseal.py` and `ai/unseal.py` (import guard tests). The API already holds one private key, the report signing key (M6).
- **Networks**: the API is on `backend` only, which is `internal: true` since M4. Only the enrich and analyst workers have `egress`. **So the API cannot reach an IdP, an SMTP relay or DNS on the internet today.** `threat_intel/ssrf.py` already has SSRF-hardened resolution and IP pinning (`resolve_pinned`, `PinnedTransport`).
- **Tenancy guard**: `tests/unit/test_tenant_session_guard.py` allowlists every `tenant_session(<org>, …)` call site; any flow that takes the org from a token (invitation accept, SSO callback) needs a vetted entry with a non-tenant lookup, the existing `*_index` pattern.
- **Sensitive actions that already carry an acknowledgement** (step-up candidates): TLP downgrade on cases and reports (`acknowledge_tlp_downgrade`), share-policy flags off, provider key PUT / DELETE (TI and AI), retention `enforce` (`acknowledge_destruction`), manual enforce runs, legal hold release, member role changes.
- **Docs**: THREAT_MODEL "Known gaps (M1)" lists *no email verification, no MFA*, *members added without consent*, *add-member enumeration*, *register 409 enumeration*, *special-use domains revisit with SSO*; PRD and ROADMAP list platform API keys, MFA, SSO, invitations and email verification as Later; DATABASE maps §11 `api_keys` to the sealed provider keys and says platform keys are not implemented.

## 2. Standards that bind the design

| Topic | Source | What it requires (short) |
|---|---|---|
| TOTP | [RFC 6238](https://www.rfc-editor.org/rfc/rfc6238) (HOTP [RFC 4226](https://www.rfc-editor.org/rfc/rfc4226)) | HMAC-SHA1 default, 30 s step, 6 digits; the verifier may accept a small window for clock drift; test vectors in Appendix B |
| Authenticators | [NIST SP 800-63B-4](https://pages.nist.gov/800-63-4/sp800-63b.html) | §3.1.4.2 "accept a given OTP only once while it is valid" (replay); OTP secret ≥ 112 bits; §3.2.2 at most **100 consecutive failures** per authenticator, then disable it; §4.2 look-up secrets (recovery codes); AAL2 reauthentication SHOULD be ≤ 24 h overall and ≤ 1 h inactivity |
| MFA practice | [OWASP MFA Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Multifactor_Authentication_Cheat_Sheet.html) | require MFA (re-auth) for sensitive actions: password or email change, disabling MFA, elevating to admin; single-use recovery codes at setup; notify the user of failed second-factor attempts and factor changes |
| OAuth / OIDC client | [RFC 9700](https://www.rfc-editor.org/rfc/rfc9700.html) (OAuth 2.0 Security BCP, Jan 2025) | authorization code flow only (no implicit); PKCE with **S256**; transaction-specific `state` / `nonce` bound to the user agent; exact redirect URI; **mix-up defence** with the `iss` response parameter ([RFC 9207](https://www.rfc-editor.org/rfc/rfc9207)) or distinct redirect URIs per issuer |
| Identity key | [OIDC Core 1.0 §5.7](https://openid.net/specs/openid-connect-core-1_0.html#ClaimStability) and the **nOAuth** class of bugs ([Semperis](https://www.semperis.com/blog/noauth-abuse-alert-full-account-takeover/), [The Hacker News, 2025-06](https://thehackernews.com/2025/06/noauth-vulnerability-still-affects-9-of.html)) | the only stable, unique user key is **(`iss`, `sub`)**; `email` is mutable and, in multi-tenant IdPs (Entra), can be set to any value by another tenant's admin. Never match accounts on `email` alone |

## 4. Key design choices and why

1. **Sealing TOTP and IdP secrets: reuse `core/sealbox` with a new domain `cyberlab.identity.v1`.** The API must open these secrets itself (it verifies codes and calls the token endpoint), so asymmetric sealing buys no separation here; reusing the format still buys domain separation (HKDF info + AAD), kid rotation, fixed error codes and the existing tests. Providers: `totp` (the AAD's uuid is the **user id**) and `oidc` (the org id, **URL-bound to the issuer**, the MISP pattern: re-pointing the issuer makes the old secret unopenable, so an admin cannot redirect the client secret to another host). A new wrapper `identity/unseal.py` becomes the third allowed importer of `sealbox_open.py`; only the api role may hold `IDENTITY_SEAL_PRIVATE_KEYS_FILE`; prod refuses the committed dev key. Residual: an API compromise reads every TOTP secret (as with any server-side TOTP); KMS / HSM later.
2. **Outbound mail is an outbox, sealed for a mail worker.** The API writes `email_outbox` rows in the same transaction as the invitation or reset, with the only secret (the link token) sealed under `cyberlab.mail.v1` with the mail worker's public key (the M4 pattern: the API encrypts only). A `mail-worker` (api image, `PROCESS_ROLE=mail`, broker user `mail`) opens, renders a **plain-text** template, sends over SMTP and nulls the sealed column. Dev / test: Mailpit on an internal `mail` network; prod: an SMTP relay through `egress`. **Tests never send real mail**: `ENV=test` accepts only the `capture` transport or the `mailpit-test` host.
3. **Tokens in URL fragments.** Invitation, reset and verification links are `{PUBLIC_BASE_URL}/invite#t=…`; the page posts the token in a JSON body. Fragments never reach logs, proxies or `Referer` (the M7 search rule). Tokens are 256-bit, stored as sha256, single-use by an atomic `UPDATE … WHERE consumed_at IS NULL AND expires_at > now() RETURNING`.
4. **Invitations replace direct add.** `POST /members` (direct add) is removed (410); invitations answer the same `201` whether or not the email is registered, which closes the M1 consent and enumeration gaps. Acceptance requires being signed in **as the invited email** or registering with it through the token (the token proves the mailbox, so the email is marked verified).
5. **MFA login is a two-step challenge, not a session.** Password OK → `202 {mfa_required}` with an HttpOnly, `SameSite=Strict` challenge cookie (Redis, 5 min, 5 attempts) and no session. Replay: an atomic `UPDATE … SET last_used_step = :s WHERE last_used_step < :s`. Window ±1 step. Throttles: per challenge, per user (10 / 15 min), and the NIST cap (100 consecutive failures → the factor is locked; recovery code or operator reset).
6. **Step-up is server-side state on the session.** A new `user_sessions` row per refresh family carries `amr`, `mfa_at`, `step_up_at`, `sso_org_id`. `core/stepup.require_recent_auth(session, user, action)` raises `403 step_up_required` unless `step_up_at` is within `STEP_UP_MAX_AGE_S` (600). Re-auth: TOTP if enrolled, else password; SSO sessions re-auth at the IdP with `max_age=0`. API keys can never step up, so every step-up action is refused for them by construction.
7. **SSO is OIDC only (no SAML), per org, behind verified domains.** Users are keyed by (`iss`, `sub`) in `user_identities`. JIT provisioning only for `email_verified = true` emails of a **domain the org verified** (DNS TXT), never admin / owner roles; linking to an existing local account only if that account's email is verified (pre-account-takeover defence) and with a notification. Home realm discovery by email domain. The callback validates `state` (single-use, Redis) bound to a `SameSite=Lax` cookie, the `iss` parameter, PKCE, nonce, `aud` / `azp`, alg allowlist (RS256 / PS256 / ES256; never `none` or HS*), `exp` / `iat` with 60 s leeway. SSO sessions are capped at `SSO_SESSION_MAX_AGE_H` (12) so IdP deprovisioning takes effect without SCIM. The callback's query (`code`, `state`) is redacted from the uvicorn access log.
8. **Platform API keys are keys of service accounts.** A service account is a `users` row with `kind = 'service'` (no password, no email login, `svc-…@service.invalid`) and an org membership capped at `analyst`, so RBAC, RLS, audit `actor_id` and the per-user limit work unchanged. Keys: `clk_<public id>_<secret>` (256-bit secret, sha256 at rest, shown once), mandatory expiry (≤ 365 days), revocable, last-use tracked (debounced), bound to one org; `Authorization: Bearer` only; CSRF is skipped only for bearer requests **without any cookie**, and a request carrying both is refused. Never stored in browser storage (one-time dialog state only).

## 5. Rejected or deferred

- **SAML**: XML signature wrapping and canonicalization bugs make it expensive to do safely; OIDC covers Entra, Google, Okta, Keycloak. Deferred.
- **SCIM**: deprovisioning relies on the SSO session cap and manual removal. Deferred.
- **WebAuthn / passkeys**: see §3; M11.1.
- **SMS / email OTP as a factor**: weaker (SIM swap, phishable) and needs a provider; email remains only the recovery channel for passwords, never a second factor.
- **"Remember this device"**: would weaken step-up; not offered.
- **Org admins resetting a member's MFA**: users are global, so an admin of one org could unlock an account that also belongs to other orgs. Only the operator script resets MFA, audited and notified.
- **Smokescreen image** and **API egress on `backend`**: see §3 and decision 1 of the plan.

## 6. Open questions for the red team

1. Is reusing the asymmetric sealbox for secrets the API itself opens worth it versus a symmetric AES-GCM keyring?
2. Does the `SameSite=Lax` SSO state cookie plus `Strict` session cookies set on the callback response work in Chromium, Firefox and Safari (the first navigation after a cross-site redirect does not carry `Strict` cookies; the web app's same-origin `fetch` afterwards does)?
3. Can the egress proxy be abused by a compromised API to reach anything that matters (it refuses non-443 ports and non-global IPs, but any public host on 443 is reachable)? Should it also enforce an issuer-host allowlist pushed from the DB?
4. Does making every step-up action refuse API keys break an automation use case that matters (for example rotating a TI key from CI)?
